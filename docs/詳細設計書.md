## 1. 設計の方針

### 1.1 守る原則

vault の「プリンシプル オブ プログラミング」の原則を、この設計では次のように当てはめる。

| 原則 | この設計での当てはめ方 |
| --- | --- |
| KISS | 要素を絡み合わせない。計算・DB・LLM・画面を別の部品に分け、1つずつ考えられるようにする。フレームワークは使わない |
| YAGNI | 今の要件にない仕組み（差し替え用のインターフェース、プラグイン機構など）は作らない。2つ目が必要になったときに作る |
| DRY | 同じ「知識」は1か所に置く。13項目の定義、設定値、文言はそれぞれ1つのファイルにだけ書く |
| OCP | 変わりやすい部分（方針）を外に出し、項目や文言を変えるときにプログラムを書き換えずに済むようにする |
| SLAP | 1つの関数の中は同じ抽象度で書く。上位の関数は手順だけを並べ、計算の細部は下位の関数に任せる |
| PIE・名前重要 | 名前で意図を表す。マジックナンバーは使わず、意味のある名前の定数にする |
| コードは必ず変更される | 大事な設計判断は「なぜそうしたか」を第14章に記録し、後から変えるときの手がかりにする |

### 1.2 「機構」と「方針」を分ける

再利用しやすくするため、コードを次の3種類に分ける。参考にした考え方は「機構と方針の分離」と「Functional Core, Imperative Shell」。

| 種類 | 中身 | 変わる理由 | 例 |
| --- | --- | --- | --- |
| 機構（mechanism） | どのアプリでも同じように使える仕組み | ほぼ変わらない | 相関係数の計算、近い順の並べ替え、LLM API の呼び出し、メール送信、DB 接続 |
| 方針（policy） | クライアントやチームの意見で変わる決まり | 意見や要望が変わったとき | 13項目の一覧、プロンプトの文章、往復数・人数などの値、画面の文言 |
| 環境設定（env） | 動かす場所ごとに違う値 | 動かす PC やサーバーが変わったとき | DB の接続先、LLM の URL、Gmail のアカウント |

- 機構は方針を知らない。方針は引数や設定ファイルとして機構に渡す。
- 方針はできるだけプログラムではなく、設定ファイル（PHP の配列）やテキストファイルに書く。プロンプトを直すのに PHP のコードを読まなくて済むようにする。
- 計算の部品（後述の Core）は DB・LLM・画面に触らない。入力を受け取って結果を返すだけにするので、ユニットテストだけで正しさを確かめられる。

### 1.3 階層（レイヤー）

上の層は下の層を呼べるが、下の層は上の層を呼ばない。

```
画面・API（public/）       … リクエストを受け取り、Service を呼び、結果を返すだけ
        ↓
Service（src/Service/）     … 1つの操作の手順を並べる（ログイン、メッセージ送信、診断）
        ↓                ↓
Core（src/Core/）     Repository・Infra（src/Repository/, src/Infra/）
 計算だけ。外部に触らない     DB・LLM・メールとのやり取り
```

## 4. API

### 4.1 共通の決まり

- すべて `POST`。送るのも返るのも JSON。
- ヘッダ `X-CSRF-Token` に、画面に埋め込んだトークンを付ける。合わなければ `403`。
- ログインが必要な API で未ログインなら `401`。
- 返事の形はそろえる（`JsonResponse` が作る）。

```json
{ "ok": true, "data": { ... } }
{ "ok": false, "error": { "code": "wrong_code", "message": "確認コードが違います。" } }
```

- `code` はプログラムが判定に使う英字、`message` は画面にそのまま出す文言（`policy/messages.php` から取る）。

### 4.2 一覧

| API | ログイン | 送るもの | 返すもの（data） | 主なエラー code |
| --- | --- | --- | --- | --- |
| `login.php` | 不要 | `email` | `redirect`（`home.php`） | `invalid_email`、`not_found`（メール認証が有効のとき） |
| `send_code.php` | 不要 | `email` | `redirect`（`verify.php`） | `invalid_email`, `send_too_soon`, `mail_failed`、`not_found`（メール認証が無効のとき） |
| `verify_code.php` | 不要 | `code` | `redirect`（`home.php`） | `no_pending_email`, `wrong_code`, `code_expired`, `too_many_attempts` |
| `logout.php` | 要 | なし | `redirect`（`index.php`） | |
| `start_conversation.php` | 要 | なし | `conversation_id`, `redirect` | |
| `send_message.php` | 要 | `conversation_id`, `content` | `reply`, `turn_count`, `can_diagnose`, `sources` | `invalid_content`, `conversation_closed`, `turn_limit`, `llm_unavailable` |
| `diagnose.php` | 要 | `conversation_id` | `course_name`, `recommendation_text`, `career_text`, `sources` | `not_enough_turns`, `conversation_closed`, `llm_unavailable` |

- `verify_code.php` のメールアドレスは、`send_code.php` のときにセッションへ入れたものを使う（画面から送らせない）。
- 会話の `conversation_id` は、ログイン中の利用者の会話かを必ず確かめる。他人の会話なら `404` を返す。

### 4.3 画面の表示

画面（`index.php` など）は PHP で HTML を作って返す。ホームのステータスやチャットの履歴は、このときに埋め込む。表示のためだけの API は作らない。

## 5. 画面

### 5.1 方針

最初はざっくりでよい。後でデザインを作り込むので、次の点を守って差し替えやすく、テストしやすくする。

- **見た目と動きを分ける。** 見た目は `app.css` だけに書く。HTML に `style` 属性を書かない。JavaScript は見た目を直接いじらず、クラスの付け外しだけをする。
- **色や角の丸みは CSS 変数にまとめる。** デザインを変えるときは変数を変えるだけで全体が変わる。
- **テスト用の目印を付ける。** 操作する部品と結果を表示する部品には `data-testid` を付ける。デザインを変えても目印は変えない。
- **状態を文字で出す。** 「送信中」「考え中」「診断中」やエラーは、アニメーションだけでなく文字でも出す。

### 5.2 デザインの決まり（仮）

```css
:root {
  --color-primary: #72bef7;   /* アイコンの空色 */
  --color-accent:  #fde68a;   /* アイコンの黄色 */
  --color-bg:      #f5faff;
  --color-surface: #ffffff;
  --color-text:    #1f2d3d;
  --color-error:   #d64545;
  --radius-card:   20px;
  --radius-button: 999px;
  --font-base: "Zen Maru Gothic", "Hiragino Maru Gothic ProN", sans-serif;
}
```

- フォントは丸ゴシック。Google Fonts が読めないネットワークでも、Mac の丸ゴシックで代わりに表示される。

### 5.3 各画面

| 画面 | 配置（上から） | data-testid |
| --- | --- | --- |
| S1 メールアドレス入力 | アイコン、アプリの説明（1〜2行）、メールアドレス入力欄、「確認コードを送る」ボタン、エラー表示欄 | `email-input`, `send-code-button`, `error-message` |
| S2 確認コード入力 | 送信先のメールアドレス、6桁の入力欄、「ログイン」ボタン、「コードを送り直す」、エラー表示欄 | `code-input`, `verify-button`, `resend-button`, `error-message` |
| S3 ホーム | ヘッダー（アイコン、ログアウト）、ステータスのカード（最も合うコース・診断日時・回数）、「新しい会話を始める」、「続きから」（診断前の会話があるときだけ） | `status-course`, `status-date`, `status-count`, `start-button`, `continue-button`, `logout-button` |
| S4 チャット | ヘッダー（「ホームへ」）、会話の履歴、状態表示（考え中・診断中）、入力欄と「送信」、「診断する」、エラー表示欄 | `message-list`, `message-input`, `send-button`, `diagnose-button`, `status-indicator`, `error-message` |

### 5.4 JavaScript の動き

- `api.js`（機構）：`postJson(url, body)` を1つだけ用意する。CSRF トークンの付加、JSON の変換、通信失敗を `{ ok: false, error: { code: "network_error", ... } }` にそろえる処理をまとめる。
- `chat.js`（S4）
  1. 送信を押したら、入力欄とボタンを無効にし、自分のメッセージを履歴に足し、「考え中」を出す。
  2. 返事が来たら履歴に足す。`can_diagnose` が true なら「診断する」を押せるようにする。
  3. エラーなら、自分のメッセージを履歴から取り除き、入力欄に戻してエラーを出す（サーバー側も保存していないため）。
  4. 「診断する」を押したら「診断中」を出し、結果を会話として足し、入力欄と「診断する」を隠して「ホームへ」を目立たせる。
- Enter で送信、Shift + Enter で改行。

## 6. ログインの処理

メール認証は `policy/app.php` の `EMAIL_VERIFICATION_ENABLED` で切り替える。

| 値 | ログインの流れ | 使う API |
| --- | --- | --- |
| `false`（2026-10-12〜13 に使用） | メールアドレスを入れるだけでログインする（`LoginService::loginWithoutVerification`）。形式とドメインの確認は 6.1 の 1.〜2. と同じ | `login.php` |
| `true`（2026-10-13 から） | 6.1・6.2 のとおり、確認コードで本人確認する | `send_code.php`、`verify_code.php` |

- 無効のときは `send_code.php` を `not_found`（404）にする。
- 有効のときに `login.php` が呼ばれたら（切り替える前に開いた画面から送られた場合）、確認コードを送って `verify.php` へ進める。確認を飛ばしてログインさせることはしない（2026-10-13 変更。前は `not_found` を返していたため、古い画面の利用者が「見つかりませんでした」で止まった）。
- 無効のときに `verify.php` を開いたら `index.php` に移す。

### 6.1 確認コードの送信（`LoginService::sendCode`）

1. メールアドレスの前後の空白を除き、小文字にする。
2. 形式が正しく、`@apps.kct.ac.jp` で終わることを確かめる。違えば `invalid_email`。
3. 同じアドレスへの直近の送信から60秒たっていなければ `send_too_soon`。
4. そのアドレスの未使用のコードをすべて使えなくする（`used_at` に今を入れる）。
5. `random_int` で 000000〜999999 のコードを作り、ハッシュにして有効期限10分で保存する。
6. メールを送る。失敗したら、作ったコードを使えなくして `mail_failed`。
7. セッションに `pending_email` を入れる。

### 6.2 確認コードの照合（`LoginService::verifyCode`）

1. セッションの `pending_email` がなければ `no_pending_email`。
2. そのアドレスの最新の未使用コードを取る。ない、または期限切れなら `code_expired`。
3. 間違えた回数が5回に達していたら `too_many_attempts`。
4. `password_verify` で照合する。違えば回数を1増やして `wrong_code`（残り回数も伝える）。
5. 正しければ `used_at` を入れ、利用者がいなければ登録する。
6. `session_regenerate_id(true)` でセッション ID を作り直し、`user_id` を入れ、`pending_email` を消す。

### 6.3 ログイン状態を1週間保つ（`Session`）

- `session.gc_maxlifetime` と クッキーの有効期限を 604800 秒（7日）にする。
- クッキーは `HttpOnly` と `SameSite=Lax` を付ける（HTTPS ではないので `Secure` は付けない）。
- セッションの保存先は `storage/sessions/` にする。MAMP・XAMPP の共通の保存先を使うと、同じ PC の他のアプリの設定でセッションが早く消されることがあるため。
- これらの設定は `php.ini` ではなく `bootstrap.php` で `session_start()` の前に行う。MAMP と XAMPP で `php.ini` を直す手間をなくすため。
- ログインが必要な画面で未ログインなら `index.php` に移す。ログイン中に `index.php` を開いたら `home.php` に移す。

## 7. チャットと診断の処理

### 7.1 会話の開始（`ChatService::start`）

1. 会話を作る（status = active）。
2. 最初のあいさつ（`policy/messages.php` の固定文）を assistant のメッセージとして保存する。LLM は呼ばない（すぐ表示でき、毎回同じ始まり方になるため）。

「続きから」は、その利用者の最新の active な会話を開く。

### 7.2 メッセージの送信（`ChatService::send`）

1. 会話がログイン中の利用者のもので、active であることを確かめる。
2. 本文を検査する（UTF-8、空でない、1000文字以内）。
3. 往復数（学生のメッセージ数）が上限（20）に達していたら `turn_limit`。
4. LLM に送る `messages` を作る：`system`（会話用の指示）＋これまでの全メッセージ＋今回の本文。
5. LLM を呼ぶ。失敗したら何も保存せず `llm_unavailable`。
6. 成功したら、学生のメッセージと返事を1つのトランザクションで保存する。
7. `turn_count` と `can_diagnose`（往復数が5以上か）を返す。

### 7.3 診断（`DiagnosisService::diagnose`）

上の層は手順だけを並べ、計算は Core に任せる（SLAP）。

```php
public function diagnose(int $userId, int $conversationId): DiagnosisResult
{
    $conversation = $this->openConversationOf($userId, $conversationId);
    $features     = $this->extractFeatures($conversation);              // LLM → 検査
    $ranking      = $this->recommender->rank($features, $this->courses->all());
    $seniors      = $this->seniorFinder->findSimilar($features, $this->seniors->all());
    $careerText   = $this->writeCareerStory($ranking->best(), $seniors); // LLM
    return $this->saveResult($conversation, $features, $ranking, $seniors, $careerText);
}
```

1. 会話が利用者のもので active、往復数が5以上であることを確かめる。
2. 特徴を取り出す（第8章 8.2 のプロンプト）。返ってきた値は `FeatureVector` で検査し、範囲外や足りない項目は3にする。
3. コースの順位をつける（第9章）。
4. 似た先輩を選ぶ（第9章）。
5. 進路紹介の文章を作る（第8章 8.2 のプロンプト）。
6. 推薦の文章を作る。これは LLM を使わず、PHP のテンプレートで作る（毎回同じ形で、根拠をはっきり示せるため）。
   - 例：「あなたに一番合いそうなのは **情報システムコース** です。特に『プログラミング・情報』『回路・電子』への興味が、このコースの学びと重なっています。」
   - 根拠の項目は、学生とコースの両方で高い項目（第9章の寄与が大きい順に2つ）。
7. 1つのトランザクションで保存する：推薦の文章と進路紹介の文章を assistant のメッセージとして保存し、診断結果を保存し、会話を diagnosed にする。
8. LLM が途中で失敗したら、何も保存せず `llm_unavailable`。もう一度「診断する」を押せる。

## 8. LLM とのやり取り

### 8.1 共通（`LlmClient`）

- `POST {LLM_BASE_URL}/chat/completions`、ヘッダは `Content-Type: application/json` と `Authorization: Bearer {LLM_API_KEY}`。
- 必ず `chat_template_kwargs: {enable_thinking: false}` を付ける。
- 接続10秒、全体120秒で時間切れ。

- `LlmClient` は方針を知らない。プロンプトや温度は呼ぶ側（Service）が渡す。

### 9.2 コースの点数（`CourseRecommender`）

学生は1〜5、コースは単位の割合で、物差しが違う。そこで、それぞれの「平均との差」で比べる。

1. **興味の点数**：学生の興味9項目とコースの興味9項目の相関係数 r を求める。
2. **学び方の点数**：
   - コース側は、5コースの平均との差を使う（理論はどのコースも57〜71%で差が小さいため、平均を引かないと差が埋もれる。vault の教訓）。
   - 学生側は、自分の4項目の平均との差を使う。
   - 2つのコサイン類似度を r とする。
3. それぞれ `(r + 1) / 2` で 0〜1 にし、重みを付けて足す。
   - `点数 = 0.7 × 興味の点数 + 0.3 × 学び方の点数`（重みは `policy/app.php`）
4. 点数の高い順に並べる。同点なら興味の点数が高い方、それも同じなら `display_order` の順。

例外の扱い：

- 学生の値がすべて同じ（例：全部3）だと、平均との差がすべて0になり、相関係数を計算できない。このときは r = 0（中間）とする。
- このため、全部3と答えた学生は、どのコースも同じ点数になる。その場合でも順番は上の同点の決まりで決まる。

推薦理由に使う「寄与」：興味の項目ごとに `(学生の値 − 学生の平均) × (コースの値 − コースの平均)` を求め、大きい順に2つを根拠にする。ただし、学生とコースの**両方が平均より高い**項目だけを数える（両方とも平均より低い項目も掛け算では正になるが、「共通の興味」ではないため。2026-10-13 修正）。

### 9.3 似た先輩（`SeniorFinder`）

- 学生も先輩も同じ物差し（1〜5）なので、13項目のユークリッド距離で比べる。値の高さそのものも似ているかを見たいため。
- 距離が小さい順に3人選ぶ（人数は `policy/app.php`）。同じ距離なら id の小さい順。
- 先輩はコースで絞らない。違うコースに進んだ似た先輩も紹介できるようにするため。

### 9.4 計算部品（`Similarity`）

外部に触らない関数だけを置く。

| 関数 | 中身 |
| --- | --- |
| `pearson(array $a, array $b): float` | 相関係数。片方のばらつきが0なら0を返す |
| `cosine(array $a, array $b): float` | コサイン類似度。片方の長さが0なら0を返す |
| `euclideanDistance(array $a, array $b): float` | ユークリッド距離 |
| `centered(array $values): array` | 平均との差 |

長さの違う配列を渡されたら例外を投げる。

## 15. 動かす環境（MAMP・XAMPP）

サーバーとして動かす PC は、Mac なら MAMP、Windows なら XAMPP を使う。どちらも Apache・PHP・MySQL がまとめて入っている。

### 15.1 両方で動かすための決まり

| 項目 | 決まり | 理由 |
| --- | --- | --- |
| 公開フォルダ | Apache のドキュメントルートを `SUISEN/public` にする | `src/` や `config/` をブラウザから見えなくするため |
| ファイルの場所 | パスは `__DIR__` からの相対で組み立て、区切りは `/` を使う | Mac と Windows でフォルダの場所や区切り文字が違っても動くようにするため（PHP は Windows でも `/` を使える） |
| 文字コード | ソースは UTF-8（BOM なし）、改行は LF | Windows のエディタで BOM が付くと、PHP の出力の前に余計な文字が出て、ヘッダやセッションが壊れるため |
| タイムゾーン | `bootstrap.php` で `date_default_timezone_set('Asia/Tokyo')`、DB 接続直後に `SET time_zone = '+09:00'` | MAMP と XAMPP で既定のタイムゾーンが違っても、有効期限の判定がずれないようにするため |
| 時刻の比較 | 有効期限などの時刻は PHP で作って DB に入れ、比較も PHP の時刻を渡して行う | PHP と MySQL の時計の食い違いを避けるため |
| PHP の拡張 | `pdo_mysql`、`curl`、`mbstring`、`openssl` を使う | どれも MAMP・XAMPP に入っていて、既定で有効。`openssl` は Gmail との暗号化した通信に使う |
| ライブラリ | Composer で PHPMailer と PHPUnit を入れる。Composer は MAMP・XAMPP の PHP で動かす | 別の PHP で入れると、バージョンの違いで動かないことがあるため |

### 15.2 環境ごとの違い

| 項目 | Mac / MAMP | Windows / XAMPP |
| --- | --- | --- |
| ドキュメントルートの設定 | MAMP の設定画面の「Server」→「Document Root」で `SUISEN/public` を選ぶ | `xampp/apache/conf/httpd.conf` の `DocumentRoot` と `<Directory>` を `SUISEN/public` に書き換える |
| Apache のポート | 既定 8888（`http://localhost:8888`） | 既定 80（`http://localhost`） |
| MySQL のポート | 既定 8889（変えられていることがある） | 既定 3306 |
| MySQL の root のパスワード | `root` | 空 |
| phpMyAdmin | `http://localhost:8888/phpMyAdmin/` | `http://localhost/phpmyadmin/` |
| 学内の他の PC から使う | Mac のファイアウォールで Apache への接続を許可する | Windows Defender ファイアウォールで Apache（httpd.exe）への接続を許可する |

### 15.3 初めて動かす手順（概要）

1. MAMP または XAMPP を起動し、Apache と MySQL を動かす。
2. ドキュメントルートを `SUISEN/public` にする。
3. phpMyAdmin で `database/schema.sql` を流す。
4. `config/env.example.php` を `config/env.php` にコピーし、DB・LLM・Gmail の値を書く。
5. `composer install` でライブラリを入れる。
6. `php database/seed.php` でコースと先輩のデータを入れる。
7. ブラウザで開いて、S1 が表示されることを確かめる。

詳しい手順は、実装の工程で README にまとめる。

## 16. 資料の検索（RAG）

2026-10-12 追加。要件定義書 F7、基本設計書 F7 を実装する細かさで決める。

### 16.1 部品と置き場所

機構（どの資料・どのアプリでも使える）と、方針（何をどう検索するか）を分ける。

| 部品 | 置き場所 | 種類 | 役割 |
| --- | --- | --- | --- |
| `TextTokenizer` | `src/Core/Search/` | 機構 | 文章を「語」に分ける（16.3） |
| `TfidfVectorizer` | `src/Core/Search/` | 機構 | 語の並びを TF-IDF のベクトルにする。ベクトルにする部分はここだけ |
| `VectorIndex` | `src/Core/Search/` | 機構 | チャンクとベクトルを持ち、近い順に返す。コースでの絞り込みもする |
| `Chunk`、`SearchHit` | `src/Core/Search/` | 機構 | チャンクと検索結果の値 |

| `SyllabusParser` | `src/Infra/` | 機構 | シラバスの詳細ページの HTML から、概要と授業計画を取り出す |

- 埋め込みに差し替えるときは、`TfidfVectorizer` と同じ「文章 → ベクトル」の役割の部品を足し、索引を作り直す。そのときに2通りになるので、共通の約束（インターフェース）を作る（今は1通りなので作らない。YAGNI）。

### 16.2 索引の作り方（`build_search_index.php`）

1. `data/syllabus/subjects_2026.csv` から、5コースの専門科目を読む。コースと学科 ID の対応は `data/courses.csv` の `department_id` 列に書く（31〜35）。
2. 各科目の詳細ページ（`data/syllabus_raw/detail/<学科ID>_<科目番号>.html`）から `SyllabusParser` で次を取り出す。
   - 概要：「概要:」の次の行。
   - 授業計画：「授業計画」から「モデルコアカリキュラム」までの間の、「N週」の次の行（その週の授業内容）。授業内容が空の週（次の行が次の週や表の終わりの見出し）は飛ばす。
   - 行の前後の空白は正規表現で除く。`trim()` はバイト単位なので、全角空白を渡すと日本語の文字を壊すため。
3. 同じ科目名で概要と授業計画がまったく同じものは、1つにまとめる（1年〜2年前期の共通科目は5コースすべての一覧に出るため）。まとめた科目は「全コース共通」とする。
4. `SyllabusChunker` でチャンクに分ける。
   - **概要チャンク：** 見出し（例：「情報システムコース／3年後期／必修／データベース」）＋概要。
   - **授業計画チャンク：** 見出し＋「授業計画：」＋週ごとの授業内容を「、」でつないだもの。`RAG_CHUNK_MAX_CHARS`（500字）を超えるときは、週の切れ目で分ける。
   - 見出しは本文の先頭にも入れる（科目名やコース名でも見つかるように）。
5. 全チャンクで `TfidfVectorizer` を学習し（IDF を求め）、各チャンクのベクトルを求める。
6. 次の形で `data/search_index.json` に保存する。

```json
{
  "method": "tfidf-char-bigram",
  "idf": { "語": 2.31, "...": 0 },
  "chunks": [
    {
      "id": "34_0046#plan1",
      "title": "C言語プログラミング",
      "label": "情報システムコース／3年後期／必修",
      "course_codes": ["information"],
      "text": "見出しと本文",
      "vector": { "語": 0.12, "...": 0 }
    }
  ]
}
```

- 索引はシラバスから何度でも作り直せるので、DB ではなくファイルにする。
- 詳細ページがない科目は、一覧の情報（科目名・コース・学年・必修選択）だけで概要チャンクを作る。
- 概要に `RAG_EXCLUDED_SUMMARY_PHRASES` の言葉がある科目は入れない（「〇〇特論A・B」は他高専・大学の授業を受講する枠だけで、授業の中身が書かれていないため）。
- 全コース共通の科目は `shared: true` を付ける。推薦・進路紹介で「このコースの授業」として挙げないようにするため。

### 16.3 ベクトルにする方法（TF-IDF）

- **語の分け方（`TextTokenizer`）：**
  - `mb_convert_kana`（`asKV`）で全角英数字・空白を半角に、半角カナを全角にそろえ、小文字にする。PHP の intl 拡張は XAMPP で既定では無効なので使わない。
  - 英数字の連続は1つの語にする（例：`php`、`ros2`）。
  - それ以外（日本語）は、記号と空白を除いて、隣り合う2文字ずつの組（文字 bigram）を語にする。日本語は単語の区切りがなく、形態素解析の辞書を入れずに済むため。
- **TF：** その語の出現回数 n から `1 + log(n)`。
- **IDF：** `log((1 + 全チャンク数) / (1 + その語を含むチャンク数)) + 1`。
- **ベクトル：** TF × IDF を、長さが1になるように割る。0 の語は持たない（疎なベクトル）。
- **近さ：** 長さ1のベクトルどうしの内積（＝コサイン類似度）。
- 索引にない語（IDF がない語）は、検索では無視する。

### 16.4 検索（`KnowledgeSearch::search`）

- 入力：検索の文章、絞り込むコースの code（なければ全コース）、件数。
- 絞り込むときは、そのコースのチャンクと「全コース共通」のチャンクを対象にする。
- 近さが `RAG_MIN_SCORE` 未満のものは捨てる（関係の薄い資料を LLM に渡さない）。
- 同じ科目のチャンクが並ぶときは、科目ごとに一番近い1つだけを残す（資料の幅を広げるため）。

### 16.5 チャットでの流れ（`ChatService::send` に足す）

1. **検索の計画（`SearchPlanner`）：** 直前の会話（`RAG_PLAN_HISTORY_MESSAGES` 件）と学生のメッセージを `plan_search.txt` で LLM に渡し、次の形で返させる。
   ```json
   { "needs_search": true, "student_asked": true, "keywords": ["データベース", "SQL"], "courses": ["information"] }
   ```
   - `courses` の値は5コースの code に縛る（`enum`）。`keywords` は5個まで。
   - JSON が壊れていたら、学生のメッセージをそのまま検索に使う（検索あり・コース指定なし）。LLM につながらないときは `llm_unavailable`。
2. **検索：** `needs_search` が true なら、キーワードと学生のメッセージをつないだ文章で `RAG_CHAT_TOP_K`（4）件を検索する。
3. **返事：** 見つかったチャンクを `{{references}}` として会話用の指示（`chat_system.txt`）に入れる。
   - 見つかったとき：「# 参考資料」として `[1] 見出し：本文` の形で並べ、「コースや授業についてはこの資料と、コースの説明の範囲だけで答える」と指示する。
   - 見つからなかったとき・検索しなかったとき：「（参考資料なし）」とし、授業の細かいことを聞かれたら「分かりません」と答えるように指示する。
3-2. **返し方の指示（2026-10-13 追加）：** LLM は、学生が質問に答えずに自分から質問したとき、答えてもらえなかった前の質問に何度も戻る癖があった。そこで次の2つを会話用の指示に入れる。
   - **これまでにした質問（`AskedQuestions`）：** 履歴の AI の発言から「？」で終わる文を取り出して並べ、「もう聞いたものとする」と伝える。
   - **今回の返し方（`turn_instruction`）：** 検索の計画で LLM に `student_asked`（学生のメッセージが質問か）も判定させる。ただし「〜してみたいです」などの話を質問と取り違えることがあるので、文の形（「？」や「〜か」「〜の」で終わる）でも確かめ、両方そろったときだけ質問とみなす。
     - 質問のとき：答えるだけにして、最後に質問を付けない。
     - それ以外：まだふれていない項目について質問を1つだけする。
3-3. **次に聞く項目（`NextTopicPicker`、2026-10-13 追加）：** 学生が質問していないときは、次に聞く項目をプログラムで決めて「『熱・流体』について聞く」のように伝える。
   - 13項目を `policy/features.php` の順に見て、まだ聞かせていない項目で、項目名の言葉（「力学・材料」なら「力学」「材料」）がこれまでの質問にも学生の発言にも出ていない最初の項目を選ぶ。
   - 聞かせた項目は `messages.topic` に保存し、同じ会話では二度と選ばない。AI が「力学・材料」を「物の動きや形」のように言い換えると、言葉の一致では分からないため。
3-4. **返事の見直し（`ReplyReview`、2026-10-13 追加）：** LLM の返事をプログラムで確かめ、問題があれば理由を伝えて1回だけ作り直させる（`REPLY_MAX_REGENERATIONS`）。
   - **実在しない授業名：** 「」で囲まれた授業名らしい言葉（〜学、〜工学、〜演習、〜実験、〜Ⅰ など）を、索引の授業名と照らす。「微生物工学Ⅰ・Ⅱ」のようなまとめた呼び方（末尾の番号を除いて前方一致）と、学生のメッセージにある言葉（引用）は問題なしとする。
   - **似た質問：** 返事の「？」で終わる文と、これまでの質問の語の重なり（ジャカード係数）が `REPLY_REPEAT_SIMILARITY`（0.45）以上なら繰り返しとする。
   - 作り直しても似た質問が残ったら、その文だけを取り除いて返す（学生にはもう聞いてある質問なので）。全部消えるときは元の返事のままにする。
3-5. **学年を指定した質問（2026-10-13 追加）：** 「3年次の情報コースの授業を教えて」のような質問は、言葉の近さで探す検索では答えられない（3年の授業だけを全部集める必要がある）。そこで次のようにする。
   - 検索の計画で、LLM に学年（`grades`、1〜5）も取り出させる。「その中で」「そのうち」のような続きの質問では、直前の会話の学年とコースを引き継がせる。
   - 学年があるときは、索引からそのコース（と全コース共通）・その学年の授業を表のように取り出し（`VectorIndex::subjectsOf`）、「授業の一覧」として会話用の指示に入れる。最大 `RAG_SUBJECT_LIST_MAX`（40）件、概要は先頭 `RAG_SUBJECT_LIST_SUMMARY_CHARS`（50）字。
   - 検索（参考資料）も同じ学年に絞る。
   - 画面の「参考にしたシラバス」には「授業一覧（情報システムコース・3年）」のように出す。
   - 索引の各チャンクに学年（`grade`）を持たせる（`subjects_2026.csv` の「学年」）。
   - 「教えて」「知りたい」で終わる文も質問とみなす。
3-6. **内部の言葉の見直し：** 返事に `REPLY_FORBIDDEN_PHRASES`（「参考資料」「授業の一覧」など、指示文の言葉）が入っていたら、言い換えるよう伝えて作り直させる。
4. **返す値：** `send_message.php` の返事に `sources`（参考にした科目の見出しの一覧）を足す。画面は返事の下に「参考：〇〇、△△」と小さく出す。
   - `sources` は DB に保存しない（会話の本文だけを保存する方針を変えないため）。読み込み直すと表示は消える。

### 16.6 診断での流れ（`DiagnosisService` に足す）

- **推薦：** 推薦したコースで絞り込み、全コース共通の科目を除いて、「根拠の項目の表示名」で検索する（根拠がないときだけ学生のメッセージで検索する。学生の発言には別コースへの質問なども混ざり、検索がぶれるため）。科目の重なりを除いて `RAG_RECOMMEND_SUBJECT_COUNT`（2）件の科目名を、テンプレート `recommendation_subjects` で推薦の文章に足す。
  - 例：「このコースでは「データベース」（3年後期）や「Webプログラミング」（4年前期）などの授業があります。」
  - 見つからなければ何も足さない。
- **進路紹介：** 推薦したコースで絞り込み、全コース共通の科目を除いて、「似た先輩の行き先」で `RAG_CAREER_TOP_K`（3）件を検索し、`career_story.txt` の `{{references}}` に入れる。「進路につながる授業があれば、参考資料の科目名を1つ挙げてよい。資料にない授業名は書かない」と指示する。

### 16.7 方針の値（`policy/app.php` に足す）

| 名前 | 値 | 意味 |
| --- | --- | --- |
| RAG_CHUNK_MAX_CHARS | 500 | 1つのチャンクの最大の文字数 |
| RAG_CHAT_TOP_K | 4 | チャットで LLM に渡す資料の数 |
| RAG_CAREER_TOP_K | 3 | 進路紹介で LLM に渡す資料の数 |
| RAG_RECOMMEND_SUBJECT_COUNT | 2 | 推薦の文章に添える科目の数 |
| RAG_MIN_SCORE | 0.05 | これより近さが低い資料は使わない |
| RAG_PLAN_HISTORY_MESSAGES | 4 | 検索の計画で LLM に見せる直前の会話の件数 |
| RAG_EXCLUDED_SUMMARY_PHRASES | `['他高専・大学等で開講される授業等を受講']` | 概要にこの言葉がある科目は索引に入れない |
| LLM_PLAN_TEMPERATURE / LLM_PLAN_MAX_TOKENS | 0.0 / 200 | 検索の計画の LLM の設定 |
| LLM_CAREER_TEMPERATURE | 0.3（2026-10-13 に 0.7 から変更） | 進路紹介の LLM の温度。データにない飾りの文を減らすため低め |

### 16.8 テスト

- `TextTokenizer`、`TfidfVectorizer`、`VectorIndex`、`SyllabusChunker` はユニットテストで確かめる（外部に触らないため）。
- `SyllabusParser` は、手元の詳細ページ1件を使ってテストする。
- 索引を作ったあと、「データベース」「ロボット」「化学実験」などで検索して、それらしい科目が上位に来るかを確かめる。

## 17. フロントエンド（React）

2026-10-13 追加。画面を、PHP のテンプレートと素の JavaScript から、React に作り直す。第5章（画面）のうち、作り方の部分（5.4 JavaScript の動き、4.3 画面の表示）はこの章に置き換える。画面の種類・配置・`data-testid`・デザインの決まり（5.1〜5.3）は変えない。

### 17.1 使うもの

| もの | 役割 |
| --- | --- |
| React、TypeScript | 画面を部品に分けて作る。API の返事の形を型で確かめる |
| Vite | 開発用サーバーとビルド |
| React Router（`HashRouter`） | 画面の移動。URL は `#/home` のような形にする。Apache の設定（書き換えの規則）を変えずに、MAMP でも XAMPP でも動くようにするため |
| Motion | アニメーション（画面の切り替え、吹き出し、診断結果の演出） |

### 17.2 フォルダ

```
frontend/                      … React のソース（ここを編集する）
├── package.json / vite.config.ts / tsconfig.json
├── public/icon.webp
└── src/
    ├── main.tsx / App.tsx     … 入口と、画面の移動（ログインしていなければログイン画面へ）
    ├── api/client.ts          … 機構：API の呼び出し（CSRF トークン、JSON、通信エラーをまとめる）
    ├── api/types.ts           … API の返事の型
    ├── session.tsx            … ログイン状態と CSRF トークンを画面全体で共有する
    ├── pages/                 … 4画面（LoginEmailPage、LoginCodePage、HomePage、ChatPage）
    ├── components/            … 見た目の部品（吹き出し、考え中の表示、ステータスのカードなど）
    └── styles.css             … デザインの決まり（色・丸み・フォントは CSS 変数）
public/app/                    … ビルドしたファイル（`npm run build` が作る。手で編集しない）
public/index.php               … `app/` へ移すだけ
```

- 画面の文言（ボタンの名前など）は React の部品に書く。エラーの文言は今までどおり API が返す（`policy/messages.php`）。
- 前の PHP の画面（`public/index.php` などの画面、`templates/`、`public/assets/`、`src/Http/View.php`）は消す。

### 17.3 API（足すもの・変えるもの）

画面を作るときに PHP が埋め込んでいたデータを、API から取るようにする。読むだけの API は `GET` で、CSRF トークンは要らない（何も変えないため）。

| API | 方法 | ログイン | 返すもの |
| --- | --- | --- | --- |
| `session.php` | GET | 不要 | `logged_in`、`pending_email`、`csrf_token`、`verification_enabled`、`code_digits`、`network_error_message` |
| `status.php` | GET | 要 | ホームのステータス（`StatusService::statusOf`） |
| `conversation.php?id=` | GET | 要 | 会話の中身（`ChatService::open`） |

- 今までの POST の API はそのまま使う。返事の `redirect` は、React の画面の場所（`/verify`、`/home`、`/chat/12`、`/`）にする。
- ログアウトするとセッションが空になり、CSRF トークンも変わるので、React は `session.php` を読み直す。

### 17.4 画面の動き（Motion）

- **画面の切り替え：** 次の画面が下から浮かび上がるように入れ替わる（`AnimatePresence`）。
- **チャットの吹き出し：** 新しい吹き出しが、ばねのように弾んで出てくる。自分の吹き出しは右から、AI の吹き出しは左から。
- **考え中：** 3つの点が順に跳ねる。
- **診断：** 診断中は表示がゆっくり脈打つ。結果は、推薦したコースの吹き出しが大きく出てきて、アイコンの黄色いきらめきが散る。
- **ホーム：** ステータスのカードが下から入り、最も合うコースの名前に黄色の下線が伸びる。
- **ボタン：** 押すと少し縮み、離すと戻る。
- 動きを減らす設定（OS の「視差効果を減らす」）になっている人には、動きを小さくする（Motion の `useReducedMotion`）。
